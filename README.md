# Mahalaxmi Enterprise ERP

Responsive ERP interface with Vercel serverless authentication and a Google Sheet as the shared source of truth for accounts, catalog, machines, production, and inventory. Google Apps Script securely bridges Vercel to the sheet. No SQL, Firebase, or Supabase database is used.

## Local development

```powershell
npm.cmd install
npm.cmd run dev
npm.cmd run build
```

Local `/api/*` requests run through the Vite middleware and use the same handlers as Vercel. To use them locally, create an untracked `.env.local` with the server variables below. Files matching `*.local` are ignored by Git.

## Google Sheets Apps Script and Vercel setup

1. Upload the master `.xlsx` file to Google Drive. In Google Sheets, open it and choose **File → Save as Google Sheets**. Keep the original `.xlsx` as a backup; the converted Sheet is the live master.
2. From the converted Sheet, choose **Extensions → Apps Script**. In **Project Settings**, enable **Show "appsscript.json" manifest file in editor**. Replace `Code.gs` with [`apps-script/Code.gs`](./apps-script/Code.gs), replace the manifest with [`apps-script/appsscript.json`](./apps-script/appsscript.json), and save both. In the Google Cloud project linked to this Apps Script project, enable the **Google Drive API**. Select `authorizeCameraClipUploads` and click **Run** once as the Apps Script owner; approve the requested scopes. This explicitly declares the Drive, Sheets, external-request, trigger, and container-UI permissions the script uses, so clip uploads do not depend on inferred scopes. Staff still approve the browser screen-share prompt once per recording session; there is no Google authorization prompt for each clip. If the owner revokes access or the required scopes change, authorization must be granted again. To install or refresh cleanup schedules separately, run `installEcommerceLabelCleanupTrigger`; it creates the hourly cleanup triggers and 15-minute chat cleanup trigger and cleans expired labels.
3. Generate an Apps Script API secret locally with `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"`. In the Sheet, choose **Mahalaxmi ERP → Configure API access**, enter this secret, and approve the requested Sheets/Drive permissions. The script stores the Sheet ID and secret in Script Properties.
4. In Apps Script, choose **Deploy → New deployment → Web app**. Set **Execute as** to yourself and **Who has access** to **Anyone**, then deploy and copy the web app URL ending in `/exec`.
5. In Vercel, open **Project → Settings → Environment Variables** and add:
   - `GOOGLE_APPS_SCRIPT_URL` — the deployed `/exec` URL
   - `GOOGLE_APPS_SCRIPT_SECRET` — the same secret entered in the Sheet menu
   - `SESSION_SECRET` — generate a different private 48-byte secret with the command above
6. Redeploy after setting the variables. If Apps Script code changes later, update the existing deployment to a new version.

Never paste either secret into chat, frontend code, or GitHub. The web app endpoint is public but requires the server-only shared secret; do not put that secret in browser code.

## Mahalaxmi Saathi private AI

- Saathi is currently deployed in FAQ-only mode: it answers verified ERP workflow FAQs and curated business-planning frameworks. Private-model calls, OpenAI text/image/voice requests, and other external AI requests are disabled server-side; this chat will not incur AI API charges. Live ERP lookups, personalized calculations, current market research, image generation/understanding, and voice transcription are unavailable in this mode. Read-aloud uses the browser/device voice.
- When external models are re-enabled, the ERP remains on Vercel and Saathi uses one chat: private ERP requests go to Ollama, while general/business prompts and media go to OpenAI only after explicit per-request confirmation. Only approved content is sent; ERP records, tasks, memory, and private chat history are not included. OpenAI replies remain in the browser session. The current FAQ-only deployment does not make these calls.
- Install Ollama and a small multilingual model on an always-on company machine. The existing 11th-generation Intel Core i5 server can be used for a pilot, but it has no dedicated GPU; test response speed before allowing five people to use it together.
- The Vercel server cannot reach an office-only computer directly. IT must create an authenticated HTTPS tunnel/reverse proxy to the Ollama `/api/chat` endpoint. Do not expose Ollama's port directly to the internet. Configure the proxy to require the same strong bearer token as Vercel.
- Add these Vercel environment variables (never add them to frontend code or Git):
  - `PRIVATE_AI_OLLAMA_URL` — the authenticated HTTPS URL ending in `/api/chat`
  - `PRIVATE_AI_MODEL` — the exact model name installed on the company Ollama server
  - `PRIVATE_AI_TOKEN` — a random secret of at least 32 characters, also configured in the HTTPS proxy
- If FAQ-only mode is later disabled, optional General AI settings belong only in Vercel server-side environment variables:
  - `OPENAI_API_KEY` — the OpenAI API key; never put it in the browser, Apps Script, source code, or chat
  - `OPENAI_MODEL` — an OpenAI API model enabled for the account; choose one that supports image input if you want image understanding
  - `OPENAI_IMAGE_MODEL` — an enabled OpenAI image-generation model ID; image generation stays unavailable until this is set
- If external AI is re-enabled, confirmed OpenAI requests may incur separate usage charges. Only approved content is sent; ERP records, tasks, private chat history, identity, and saved memory are excluded. OpenAI has no web-search capability in this integration, so it cannot verify current market size, competitor information, or other live facts. Verify time-sensitive answers independently.
- When external AI is enabled, general/business prompts can cover business plans, market-research frameworks, customer segmentation, competitor-analysis methods, SWOT, pricing/unit economics, and go-to-market strategy. Image understanding and generation need enabled models and may incur charges; generated images are not saved by this app.
- If external AI is enabled, voice input records up to 30 seconds, caps the file at 2 MB, and requires confirmation before transcription. The transcript is inserted into the composer for review; submitting it requires separate confirmation. Voice recordings are not stored by this app.
- OpenAI's Videos/Sora API shut down on 2026-09-24; this app does not offer video generation. Granting a Videos permission does not restore that API. A separate supported video provider is needed for video generation.
- When private AI is re-enabled, use `http://127.0.0.1:11434/api/chat` only for local development; production requires HTTPS and a server-only token. Redeploy Vercel after configuration. The `/api/erp` function has a 75-second limit for media requests.
- Saathi FAQ lookup includes English, common Hinglish, Hindi, and Gujarati terms; FAQ answers are currently in English. The verified set covers documented ERP workflows and troubleshooting, plus curated business strategy, market-research methods, competitor comparison, unit economics, and measurable promotion planning. These business answers are static frameworks, not personalized advice or live market research; verify all inputs and current facts independently. Add or correct FAQ entries in `api/_lib/assistantFaq.ts`. FAQ-only answers are labeled and never claim to have checked live ERP data. To re-enable external/private model calls later, change `SAATHI_FAQ_ONLY_MODE` in `api/erp.ts` and redeploy after verifying provider access, privacy, and billing settings.
- Active private ERP assistant history is private and expires after 24 hours of inactivity. Cleanup archives the transcript to the Apps Script owner's private Drive Trash, where Drive normally permanently deletes it after 30 days. A separate per-user memory summary remains in a private spreadsheet until that user clears it in Saathi. Clearing memory does not remove unexpired chat history. General AI questions and replies are kept only in the open browser session and are not written to Apps Script, chat history, or memory.
- After replacing `apps-script/Code.gs`, update the existing Apps Script deployment to a new web-app version and run `installEcommerceLabelCleanupTrigger` once as the Apps Script owner. This installs or refreshes the 15-minute cleanup trigger used for both employee Chat and assistant chat. The assistant is added to the existing `/api/erp` route to stay within the Vercel function limit.

## Accounts and roles

- The first Admin is created once through the setup link after the Apps Script connection is configured.
- The `Users` worksheet is added to the Google Sheet when the first Admin is created.
- Passwords are stored as salted PBKDF2 hashes; raw passwords are never written to the workbook.
- Users can change their own password from **Change Password** after verifying the current password. The Super Admin can set a new password for any account in **User Management**; the current password is never displayed.
- The Admin creates non-admin accounts from **Create team login** or **More → User Management**.
- When creating an E-commerce Executive, the Super Admin can leave the reporting manager unassigned and assign an active E-commerce Manager later in **User Management**. E-commerce Managers creating executives are assigned as their manager automatically.
- `/admin` is for the single Super Admin; team members use the main login page. Reload restores the signed-in workspace from its HttpOnly session cookie; protected API requests still verify the active account and role against the connected Users sheet.
- After sign-in, Super Admin and Production Supervisor can use the operational ERP modules, including catalog, machines, inventory, stock movements, shipping, and returns. The Super Admin has read-only access to Shipping & Delivery and Returns & RTO; only the Production Supervisor can record dispatches, returns, or damage. The Employees directory lists non-admin user accounts from the shared Users sheet, including newly created team accounts. Super Admin and Production Supervisors can add suppliers; Production Supervisors manage supplier status. Only Super Admin can open Employees, Accounts, Reports, User Management, Settings, and Audit Logs. Only the Production Supervisor can enter production records; Super Admin and Machine Operators can inspect them. Store Manager accounts retain dashboard access. All active roles can use Chat.
- The Super Admin creates **E-commerce Manager** accounts and assigns daily and monthly order targets to them. Admins can create E-commerce Executives with an active manager or leave them unassigned and link them to a manager later in User Management; an E-commerce Manager can also create executives, who are automatically linked to that manager. Each executive receives an independent assignment of one or more Amazon, Flipkart, Meesho, Shopify, or Myntra platforms. The manager workspace is restricted to that manager's executives, their assigned platforms, daily reports, assigned tasks, and team activity. Managers can set targets, assign dated tasks to their own executives, review task completion and team reports, submit one private daily work report from the sidebar, and activate or deactivate their own executive accounts. Managers can edit their own report for the day; reports are stored in the private E-commerce Daily Reports Drive folder. Executives update task progress and submit completed tasks for manager review. Tasks are stored in the `Ecommerce_Tasks` sheet, created with a Drive backup on the first write. Admins can reassign executives and view all teams' tasks from User Management.
- The executive workspace shows only the executive's assigned listings, finished-goods stock, dispatches, returns, damage, and reports. Executives can update the Platform SKU, MRP, and selling price only for assigned marketplace listings, upload a shipping-label PDF, and submit a daily report with completed work, pending work, and issues/notes. These listing edits do not change the shared ERP Product SKU. Reports are stored in a separate private Drive folder; executives can view their own latest saved report, the owning manager can view reports from direct reports, and the Super Admin can view all executive reports.
- The Super Admin dashboard includes month-filtered dispatch/return/damage analysis, manager and executive targets, daily reports, and an Excel export. Admins set daily and monthly targets for managers; managers set targets for their executives. Executive actuals use unique dispatched order numbers across that executive's assigned platforms. Manager actuals use unique dispatched order numbers once across the union of active direct reports' platforms, avoiding double-counting orders when the team shares a platform. No marketplace API connection is used. Targets are stored in Apps Script Script Properties; account reporting links are stored in the Users sheet's `Manager ID` column. Existing Users sheets are migrated automatically by adding the `Manager ID` header on the next account write.
- The Super Admin can create a **Sales Executive** account. Sales Executives see only their assigned leads and orders, can log call/WhatsApp/meeting updates with an outcome and next follow-up date, see active finished-goods availability, and book orders for an assigned lead or a one-time customer name. The Super Admin imports 1–500 lead rows from the first sheet of an `.xlsx`, `.xls`, or `.csv` file; Contact Name and Phone are required, and an optional HTTPS `Reference URL` can point to a PDF or form. The import template supports an optional `Assigned To` username/name column and an Admin-selected default assignee; duplicate phone numbers are skipped. The Admin can also add a lead manually and reassign existing leads.
- The Super Admin can create a **Graphic Designer** account. Designers manage product-linked social posts and videos in **Graphic Design**, schedule each task within a selected month, choose one or more platforms (Instagram, Facebook, YouTube, or LinkedIn), and provide a creative brief, caption, and video script/shot list. Shoot and edit progress are tracked separately. Tasks are stored in the `Graphic_Design_Tasks` sheet with a Drive backup before each write. Designers have a dedicated **Daily Work Report** sidebar page to submit and update one private report per day with completed, pending, and issue notes; reports are stored in a private Drive folder created automatically on the first report. The Super Admin can review all submissions, approve or reject them with a note, view the monthly schedule and scripts, and read all Graphic Designer daily reports.
- **Daily Tasks** is available to every active non-admin employee. The Super Admin can assign dated tasks to all active employees, selected roles, or selected employees using a simple form with text instructions and an optional private PDF/TXT reference (up to 3 MB). Each employee can save progress and submit completed, pending, and issue notes; the Super Admin can approve the report or request changes. Assignments are stored in `Daily_Tasks` with a Drive backup before writes. Attachments stay private and are downloadable only by the Super Admin and assigned employee. The existing E-commerce Manager-to-Executive task workflow remains separate.
- Sales orders save the unit price and total amount and reserve finished-goods stock immediately; booking is rejected if the current available balance is insufficient. A booking always uses an active inventory SKU; an optional custom product name changes only the name saved on that order and never creates or updates a catalog product or marketplace listing. Custom customer names are also stored on the order only and do not create leads. Sales Executives can submit one daily work report with completed, pending, and issues/notes fields; submitting again updates that day's private report. Executives can see their own reports, while the Super Admin and Production Supervisor can review all Sales reports. Sales targets are set per Sales Executive and month (`YYYY-MM`) or year (`YYYY`), and actuals update from booked order amounts minus cancelled units. A salesperson can cancel their own unfulfilled quantity; the Super Admin can cancel any order. The Production Supervisor has read-only access to all leads, orders, reports, and targets. To dispatch a booked order, the Production Supervisor selects **DIRECT** in Shipping & Delivery and links the `ORD-…` order ID; dispatch consumes that order's reservation. Sales reports export target summaries, monthly orders, leads, and activity history to Excel. `Sales_Leads`, `Sales_Activities`, `Sales_Orders`, and `Sales_Targets` tabs are created on first write with a Drive backup.
- E-commerce users have role-appropriate sidebar links for the workspace overview, stock/SKUs, dispatches/returns, shipping labels, and daily reporting for both Executives and Managers. Graphic Designers have a separate Daily Work Report sidebar page. All employee roles can use Daily Tasks to report on Admin-assigned work. The stock page searches product names, product SKUs, and platform SKUs. Dispatched orders are counted by unique order number; the ledger does not currently record delivery confirmation.
- **Marketplace Reconciliation** lets the Super Admin import supported marketplace order and settlement reports for any supported platform and review consolidated totals. E-commerce Executives can import reports only for platforms assigned to their account. Imports accept XLSX, XLS, CSV, or supported ZIP files up to 25 MB, in batches of 500 rows; duplicate source records are skipped. Progress is shown during extraction and row-batch uploads, which are written to the sheet in one operation per batch. The Admin dashboard updates from confirmed imported rows without reloading the full reconciliation history. Deploy the latest `apps-script/Code.gs` as a new web-app version to enable the bulk-write and response changes. The Super Admin must use this page to upload reports; it does not connect to marketplace APIs or automatically sync transactions.
- Shipping-label PDFs (maximum 3 MB) are kept in a private Drive folder and permanently deleted after 7 days by an hourly Apps Script cleanup trigger installed once with `installEcommerceLabelCleanupTrigger` in the Apps Script editor. Listing, upload, and download also clean up expired labels. Normal app requests do not inspect or create project triggers, so they do not require the `script.scriptapp` scope. The app never returns a public Drive link. E-commerce Executives can access only labels for their assigned platforms, E-commerce Managers can access labels for their active direct reports' platforms, and Production Supervisors can access labels for all platforms. Super Admins do not have Shipping Labels module access. Downloads are streamed through an authenticated server route. The Apps Script owner must authorize the trigger and external requests, and enable the Drive API for permanent deletion.
- User creation and status changes create a Drive backup before updating the Google Sheet.

## ERP activity audit

- The signed-in app discloses that successful sign-ins/sign-outs, ERP module visits, selected business-record write attempts, and screen-recording start/stop events are logged. Write events show the actor, role, time, action, a limited ERP record identifier where available, and outcome; they do not store passwords, request bodies, customer details, keystrokes, or browser/Google history.
- Webcam capture is never automatic. A team member must press **Start screen + webcam**, approve the browser's screen-share and camera prompts, and can stop at any time. The approved screen is streamed live to **Camera Monitoring → Live shared screens**; the webcam is composited as a picture-in-picture overlay only in saved clips and is not streamed live. Selecting an entire display may include other visible tabs or apps. Each independently playable five-minute WebM clip is saved privately under `Mahalaxmi ERP/04 Screen Recordings/Mahalaxmi ERP Private Camera Recordings/<team member>`, appears under **Screen recordings** after upload completes, and is moved to Drive Trash after 24 hours. Drive permanently removes trashed recordings after 30 days. Signing out stops capture and uploads the final clip. No audio, keystrokes, or browser history are recorded.
- Chat provides direct messages between active team accounts, with text and JPEG/PNG/GIF/WebP/PDF attachments up to 3 MB. A short-lived, authenticated typing indicator is polled only for the open conversation and is not stored with messages. Conversation data and files are stored separately from the ERP workbook in private Apps Script-owned Google Drive resources; links are never made public. Participants can read their own conversations, and the Super Admin can view all conversations and attachments. The chat screen discloses this access model. Messages are hidden after 48 hours and a 15-minute Apps Script trigger permanently deletes expired messages and attachments (cleanup may therefore be delayed by up to about 15 minutes). The Apps Script owner must run `installEcommerceLabelCleanupTrigger` after deploying the updated script and authorize its Drive/Sheets scopes.
- Mahalaxmi Saathi is a separate, read-only helper available to active roles. The Private ERP assistant uses the signed-in user's role, curated ERP workflow guidance, relevant role-filtered ERP records, and allowed Daily Tasks when needed; it does not send the full workbook to the model. With the private model connected, it replies in the user's language; Enter sends a message and Shift+Enter adds a line. Without the private model, only verified matching FAQs are available for ERP guidance, not live ERP answers. General questions can be answered through OpenAI only after the user confirms the request; OpenAI receives no ERP data or live web search context. The API key remains server-side only.
- The Super Admin can review the latest 500 events in **Audit Logs**; the view refreshes every 30 seconds. Events are stored in a separate private spreadsheet owned by the Apps Script account and are deleted after 90 days. Access to the API view is restricted to the Super Admin.
- ERP spreadsheet backups are created before writes. The hourly cleanup keeps the newest backup and permanently deletes other ERP backup copies older than 30 days. After updating `apps-script/Code.gs`, update the existing Apps Script web-app deployment to a new version and run `installEcommerceLabelCleanupTrigger` once again. This installs the hourly audit/label/camera/backup cleanup triggers and the 15-minute chat-retention cleanup trigger. Private audit and chat storage are created automatically when first needed; Apps Script may request Drive/Sheets authorization. Redeploy the Vercel app after deploying the script.

## Screen sharing and recordings

- Webcam capture is requested only after the team member starts recording and approves the browser's camera prompt. It is not recorded on its own or broadcast live; it appears as a picture-in-picture overlay in the saved screen clip. No microphone is requested.
- Screen sharing is user-started only. The persistent ERP control requests native screen-sharing and camera permissions and displays a visible recording status and Stop control. Approved screens stream live to **Camera Monitoring → Live shared screens**; saved clips include the approved webcam overlay. Each five-minute segment starts a fresh recorder so its WebM file plays independently, and appears under **Screen recordings** after Drive confirms upload.
- The Apps Script deployment owner must install [`appsscript.json`](./apps-script/appsscript.json), run `authorizeCameraClipUploads` once, and approve external-request/Drive access before clips can upload. Deploy the web app to execute as that same owner. If uploads still fail, check **Apps Script → Executions** for the logged failing action (`startCameraClipUpload` or `uploadCameraClipChunk`); the request error is logged with upload tokens redacted. Google authorization is not requested for each clip.
- Camera API routes and authentication endpoints are consolidated so the project stays within Vercel Hobby’s 12-function deployment limit.
- Screen clips are stored privately in the Apps Script owner's Drive and count against that account or shared-drive quota. Run `organizeMahalaxmiErpDrive` once from the Apps Script editor or **Mahalaxmi ERP → Organize ERP Drive** in the master spreadsheet to move the workbook and existing ERP Drive resources into the private `Mahalaxmi ERP` parent folder. It creates separate folders for the main spreadsheet/backups, chat, audit logs, screen recordings, Graphic Design, E-commerce, and Sales; future generated files use the same structure. At 500 kbps, ten hours of screen recording can use about 2.25 GB. Live sharing also requires valid LiveKit credentials.

## Shared catalog, production, and inventory workflow

- The Super Admin or Production Supervisor can manage products, variants, and marketplace SKUs in **Product Catalog**. Select a master product to see its variants and linked listings together. Marketplace listings link a selected active product/variant to a platform SKU; Amazon.in, Amazon.com, Flipkart, Meesho, Myntra, and Shopify are supported. A platform SKU may be reused on a different platform but must be unique within its platform. Listings are stored in the `Marketplace_Listings` tab.
- The Super Admin and Production Supervisor can add suppliers to the **Suppliers** registry; only the Production Supervisor can activate or deactivate them. Creating a raw material requires an active supplier, and each **Purchase Inward** requires a supplier and unit cost. Supplier ID/name, unit cost, and purchase total are stored on each stock-movement row so monthly purchase totals can be grouped by supplier. `Suppliers` is created on the first supplier write, with the normal pre-write Drive backup.
- **Accounts** lets the Super Admin record dated, categorized expenses with payment method and optional reference. **Reports** provides a month selector for financial and operational summaries plus an Excel export. Financial reporting counts revenue when a finished-goods dispatch is posted, uses the sale price captured on that dispatch, subtracts recorded returns/damage, and shows recorded supplier purchases and manual expenses. The “Net tracked balance” is a limited operational measure, not accounting profit. Historical dispatches or purchases without saved prices/costs are excluded and identified rather than estimated. `Accounts_Expenses` is created on the first expense write, with the normal pre-write Drive backup.
- Marketplace listing records keep both MRP and platform selling price. The combined workbook import reads `Selling Price` and `MRP` (with `MRP (INR)` or `List Price` fallback), and the catalog and e-commerce stock tables display both amounts. Existing marketplace listings can be updated by their stable Listing ID, including Platform SKU and prices; a changed Platform SKU does not change the shared ERP Product SKU.
- E-commerce monthly reports in the E-commerce workspace calculate gross sales from dispatched units × the current platform listing selling price, then subtract return and damage values for net sales. Changing a listing's selling price therefore affects those E-commerce report calculations for that SKU/platform pair, including earlier ledger movements. The ERP **Reports** module instead uses the unit price saved at dispatch time.
- In **Product Catalog**, Admins and Production Supervisors can use **Import workbook** to merge rows from `Products_Import`, `SKU_Variants_Import`, and `Marketplace_Listings_Import` in the prepared `.xlsx` file into the existing configured Google Sheet. Matching products are identified by stable product ID, existing SKU, or a unique case-insensitive exact title; ambiguous title matches fail rather than guess. Nonblank changed values update existing products, variants, and listings, while blank cells and unchanged values are preserved. A product SKU rename updates linked variants, listings, and current finished-goods stock, records the former SKU for historical price lookup, and leaves historical stock-movement and production logs unchanged. New rows are added, one Drive backup is created before writes, and no rows are deleted. Source-report tabs are not imported.
- **Excel Management → Reset ERP data** is a separate, Super-Admin-only action. After the operator types `RESET ERP`, the deployed Apps Script makes private copies of the master and chat workbooks, archives the private report/media/attachment folders in Drive, clears all data rows while preserving sheet headers and the signed-in Super Admin, and removes target settings for cleared users. The existing audit history and app/deployment configuration are retained. Deploy the updated Vercel app and latest Apps Script version; the Apps Script owner must approve Drive/Sheets authorization if prompted. A reset is not complete until the UI reports its private backup folder.
- Production Supervisors can search the global SKU search by product SKU or marketplace SKU and see the linked product, platform, and platform-specific SKU. Marketplace SKU mappings do not replace the internal production SKU.
- Active SKUs are read from the Google Sheet for team accounts. When a product has active variants, production shows those variants instead of an ambiguous parent SKU; the selector displays product name, SKU, size, and color.
- The Super Admin assigns production targets by machine and product for a selected day, week (Monday–Sunday), or calendar month. Existing active catalog SKUs are selectable; an unlisted item can be entered as a target-only custom name without creating a catalog record. Production Supervisors can see all targets and actual-versus-target progress; Machine Operators see targets only for machines assigned to them. Progress is calculated from production entries in the target period, and saving the same machine/product/period updates the target instead of creating a duplicate.
- Machine entries save name, type, operator, and status to the `Machines` sheet. Machine type includes a selectable **Stitching Machine** option and retains existing/custom types. Stitching reports include only machines whose type contains “Stitching.” Department is omitted from the machine form, roster, and Excel export; existing workbook values are left untouched. Supervisors and operators can select configured, non-maintenance machines; the Super Admin or Production Supervisor can manage the machine list.
- Only the Production Supervisor can submit production entries or QC decisions; Super Admin and Machine Operators can inspect production records. Entries select a scheduled time block (Block 1, 2, or 3) along with the machine and SKU. Production dates, dashboard weekday labels, and today's records use the India calendar; movement timestamps display in India time (IST). For today's entries, the active block is automatically selected using India time; during breaks or outside scheduled hours, and for other dates, it can be selected manually. The selected block is saved with each production record in the `Production` sheet. New production starts as **Pending QC** and does not increase available finished-goods stock. QC pass/reject quantities must equal the batch output, and only approved units increase stock and create a QC stock movement. Legacy production rows remain treated as already reviewed to avoid changing existing stock. The **Stitching** and **Quality Control** reports show batch/date/block/SKU, machine, output, pass/reject, stock, and period target/actual/shortfall; overlapping daily, weekly, and monthly targets are reported separately. The API adds `Variant SKU`, `Production Block`, and QC columns as needed.
- **Raw Material** creates raw-material records and supports purchase inward, issue, machine/stitching consumption, wastage, and stock adjustments. **Finished Goods** supports opening stock, dispatch, returns, damage, reservations, and adjustments. These modules are read-only for the Super Admin; Production Supervisors add and manage materials and stock, including dispatches, returns, damage, and the one-time zero-stock initialization. The initialization sets active SKUs with missing, zero, or negative balances to 10,000 through auditable adjustment-in ledger entries; raw materials and SKUs already above zero are unchanged.
- **Inventory** summarizes raw-material and available finished-goods balances. **Shipping & Delivery** is read-only for the Super Admin; Production Supervisors record a channel (Amazon, Flipkart, Meesho, Shopify, or Myntra), a delivery partner, SKU, order number, and quantity, then post the dispatch. The order number links later returns and damage entries to the dispatch. Delivery notes are optional, but dispatches cannot reduce available stock below zero. Product SKUs are filtered by the selected channel's active marketplace listings. Amazon includes Amazon and Amazon Flex partner choices; Shopify and Myntra include their own delivery choices; all channels include Shree Anji Courier and Delivery App, with a custom partner option when needed. **Returns & RTO** is also read-only for the Super Admin; Production Supervisors can select a platform and shipped order/SKU, then record a partial return or damage up to the remaining shipped quantity. Sellable returns increase available stock; damaged returns are recorded as returned and damaged without being added to sellable stock. The existing manual stock-movement entry remains available for older deliveries without an order number. These operations update the live Sheet through a script lock and create a Drive backup before changing balances. Stock balances and the inventory ledger are withheld from Machine Operator and Store Manager roles.
- **Stock Movement** is the append-only audit ledger. Posted movements cannot be deleted; correct them with an adjustment. A zero-balance item with history can only be archived. A zero-balance item without history may be deleted.
- Long inventory, catalog, production, stock-ledger, user, report, and e-commerce tables and activity/label lists show 10 rows at a time, with 25- and 50-row options when needed. Search and filters apply before pagination; paging changes only the displayed rows.
- The workbook tabs `Raw_Materials`, `Finished_Goods`, and `Stock_Movement` are required for live inventory operations. The Apps Script adds inventory adjustment/status, ledger item-type, sales-channel, and delivery-partner columns when needed.
- A valid signed-in startup verifies the account and returns the dashboard workbook in one Apps Script call. E-commerce roles load only their account data instead of all ERP workbook tabs. Apps Script caches workbook sheets for up to 30 seconds (gzip-compressing cache entries when that allows larger sheets to fit) and invalidates the cache after app writes; direct edits in Google Sheets may take up to 30 seconds to appear. The server coalesces concurrent workbook reads and reuses the result for up to 30 seconds, clearing it after writes. Once the deployed script advertises same-request session validation, inventory writes avoid a separate user lookup and validate the account in the write request; older deployments safely keep the extra validation call. Returning to a visible signed-in browser refreshes workbook data no more than once every 30 seconds. Successful Sales writes update the affected screen state from the save response instead of triggering an additional full-workbook reload.
- Writes create a Drive backup and Apps Script locks edits to avoid concurrent row writes. The Apps Script source in `apps-script/Code.gs` must be deployed as a new version after changes.

## Current scope and cautions

The converted Google Sheet is the live master. Changes made by the app do not update the original `.xlsx` backup; download/export the Google Sheet as Excel when an `.xlsx` copy is needed. The local `public/Mahalaxmi-Enterprise-Master.xlsx` is a read-only preview copy and is not the deployed source of truth.

Excel file uploads under **Excel Management** are validation previews only; use **Product Catalog → Import workbook** for the prepared catalog import. Some non-inventory ERP screens are still frontend-only; do not treat those as synchronized writes. The current SheetJS `xlsx` dependency has a high-severity audit advisory with no available fix. Use only trusted files until the parser is replaced.
